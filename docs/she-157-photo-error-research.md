# SHE-157 photo-processing error research

Research checked against installed Expo SDK 55 packages on 2026-09-28: `expo-image-manipulator` 55.0.20, `expo-image-loader` 55.0.1, `expo-file-system` 55.0.25, and `expo-image-picker` 55.0.23.

## Findings

- **The Android message does not identify a root cause.** ImageManipulator's Android `renderAsync` awaits its image-loading task. On load failure, Expo wraps the cause as `Could not load the image: …`; the Android image loader's Glide failure callback replaces the loader detail with the generic `Loading bitmap failed` exception. Neither message classifies the failure as RAM, storage, URI access, or image data. [ImageManipulatorModule.kt](https://github.com/expo/expo/blob/sdk-55/packages/expo-image-manipulator/android/src/main/java/expo/modules/imagemanipulator/ImageManipulatorModule.kt#L35-L53) · [ImageLoaderService.kt](https://github.com/expo/expo/blob/sdk-55/packages/expo-image-loader/android/src/main/java/expo/modules/imageloader/ImageLoaderService.kt#L67-L90)
- **RAM and storage are different failure classes.** Android documents decoded bitmaps as memory-intensive; for example, a 4048 × 3036 `ARGB_8888` bitmap takes about 48 MB. This supports RAM pressure as a plausible decode failure, but does not prove it caused this report. [Android: Loading Large Bitmaps Efficiently](https://developer.android.com/topic/performance/graphics/load-bitmap)
- **Low disk space is plausible for file creation/writes, but not diagnosed by this message.** Expo ImageManipulator's helper awaits `renderAsync()` before `saveAsync()`; its Android `saveAsync` then opens a `FileOutputStream` for the output. Expo ImagePicker also processes images into its cache directory. Thus a full filesystem can affect input/output file operations, but the reported render/load error occurs before ImageManipulator's output write, and Expo's loader code does not translate “disk full” into that message. [ImageManipulator.ts](https://github.com/expo/expo/blob/sdk-55/packages/expo-image-manipulator/src/ImageManipulator.ts#L24-L53) · [ImageManipulatorModule.kt](https://github.com/expo/expo/blob/sdk-55/packages/expo-image-manipulator/android/src/main/java/expo/modules/imagemanipulator/ImageManipulatorModule.kt#L107-L135) · [MediaHandler.kt](https://github.com/expo/expo/blob/sdk-55/packages/expo-image-picker/android/src/main/java/expo/modules/imagepicker/MediaHandler.kt#L43-L73)
- **Expo exposes an absolute available-space reading.** In the installed FileSystem API, use `Paths.availableDiskSpace` (bytes); `Paths.totalDiskSpace` is also available. The Android implementation reads the app files directory's `freeSpace`. Expo documents `Paths.cache` as storage the system may delete when the device is low on storage. A “99% full” indicator alone does not reveal how many bytes remain or prove this error was caused by storage. [Expo FileSystem SDK 55](https://docs.expo.dev/versions/v55.0.0/sdk/filesystem/) · [Expo FileSystem.ts](https://github.com/expo/expo/blob/sdk-55/packages/expo-file-system/src/FileSystem.ts#L1-L60) · [FileSystemModule.kt](https://github.com/expo/expo/blob/sdk-55/packages/expo-file-system/android/src/main/java/expo/modules/filesystem/FileSystemModule.kt#L50-L56)

## Error-classification takeaway

Treat `Could not load the image` / `Loading bitmap failed` as an **image-source load/decode failure with an undisclosed cause**, not as an out-of-memory or out-of-storage diagnosis. RAM exhaustion is consistent with Android bitmap-loading constraints; storage exhaustion is a separate possibility for cache/output writes, but these Expo messages do not establish it. `Paths.availableDiskSpace` can support a low-storage-specific message only when the app has independent evidence of a failed write or very low available bytes; this error string by itself is insufficient.
